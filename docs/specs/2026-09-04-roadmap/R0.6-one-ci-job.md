# R0.6 — One GitHub Actions job that runs the suite on Linux

**Roadmap item:** `docs/ROADMAP.md` R0.6
**Depends on:** R0.1, R0.2, R0.3, R0.4, R0.5 — all of them. A CI job added
before those land is red on its first run, and a red CI job that everybody
knows is red is worse than none.
**Blocks:** nothing mechanically; in practice it is what keeps every later
spec's acceptance table honest.
**Size:** S
**Decision needed first:** none for the job itself. One thing it *exposes*
needs the owner and is recorded in §6.

---

## 1. Context

Nothing runs Deckle's 1531 tests except a person, on the machine they happen
to be sitting at. There is no `.github/` directory at all:

```
$ ls .github
".github": No such file or directory (os error 2)
```

The four defects R0.1-R0.4 describe are all of one kind: **things that are
true on the author's Windows machine and false everywhere else.** A missing
fixture that one working tree happened to have. A `numpy` import that one
environment happened to satisfy. A build recipe that one checkout happened
to contain. A `chmod` constant that means one thing on Windows and another
on POSIX. Every one of them would have failed on the first push to a Linux
runner, and the whole class of them is what a second machine catches.

That is the argument for this job, and it is worth stating in the narrow
form: **not "CI is good practice" but "these four bugs, this month, would
have been caught in three minutes each."**

The suite is fast enough for this to be cheap. Measured on a fresh clone
here: `49.68s` wall for the full run.

## 3. Change

One new file, `.github/workflows/test.yml`, with exactly this content. No
other file changes.

```yaml
# The suite, on a machine that is not the author's.
#
# Every one of R0.1-R0.4 was a defect that was true on one Windows working
# tree and false everywhere else: a test fixture that was never committed,
# an undeclared numpy import, a build spec swallowed by `*.spec`, and a
# `chmod` constant that means "writable" on Windows and "unreadable" on
# POSIX. All four would have failed on the first push here. That is what
# this job is for -- not coverage, not gatekeeping, just a second machine.
name: tests

on:
  push:
    branches: [main]
  pull_request:
  workflow_dispatch:

# A push that supersedes an in-flight run cancels it. The suite is ~50s;
# this is about not queueing behind yourself, not about cost.
concurrency:
  group: tests-${{ github.ref }}
  cancel-in-progress: true

permissions:
  contents: read

jobs:
  pytest:
    runs-on: ubuntu-latest
    timeout-minutes: 20
    strategy:
      # Both interpreters report. A failure on one is a fact about that
      # one, and cancelling the other throws away the comparison that
      # makes it diagnosable.
      fail-fast: false
      matrix:
        python-version: ["3.12", "3.14"]

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python-version }}
          cache: pip
          # There is no lockfile; the extras live in pyproject.toml, so
          # that is what the cache key hashes.
          cache-dependency-path: pyproject.toml

      # PySide6 ships its own Qt, but Qt still links the system's EGL,
      # fontconfig, xkbcommon and dbus. Without these the offscreen
      # platform plugin fails to load and every Qt test dies with
      # "could not load the Qt platform plugin" rather than an assertion.
      # No X server and no Xvfb: nothing in the suite needs a display.
      - name: Install the libraries Qt links against
        run: |
          sudo apt-get update
          sudo apt-get install -y --no-install-recommends \
            libegl1 \
            libopengl0 \
            libglib2.0-0 \
            libdbus-1-3 \
            libfontconfig1 \
            libfreetype6 \
            libxkbcommon0

      - name: Install Deckle and its test extras
        run: |
          python -m pip install --upgrade pip
          python -m pip install -e ".[dev]"

      # Printed rather than asserted. This is the first thing a bug report
      # asks for, and it exercises the importlib.metadata path that the
      # frozen build once got silently wrong -- a "not installed" here
      # would be worth knowing about before it reaches a bundle.
      - name: Report what is installed
        run: python -m deckle.cli --version

      - name: Run the suite
        env:
          QT_QPA_PLATFORM: offscreen
        run: python -m pytest -q --no-header -p no:cacheprovider
```

### Notes on choices made, so nobody has to re-decide them

- **No fixture-generation step.** R0.1 commits
  `tests/fixtures/sample.pdf` rather than generating it, so `checkout` is
  enough. If R0.1 is ever revisited in favour of generation, the step to add
  here is `python -m deckle.cli dummy -o tests/fixtures/sample.pdf --pages 2`
  before the pytest step — **not** `python -m deckle`, which launches the GUI
  and blocks the runner until the 20-minute timeout.
- **No `numpy` install.** R0.2 removes the only use.
- **`python -m pytest`, not `pytest`.** Same reason the rest of the project
  does it: it puts the working directory on `sys.path` and pins which
  interpreter is running.
- **`-p no:cacheprovider`** matches `00-environment.md` and keeps the runner
  from writing a `.pytest_cache` nothing reads.
- **Linux only.** Windows is where the code is written and is continuously
  "tested" by being used; Linux is the machine nobody has. A Windows job
  would also need `run.bat`'s own path and is not free. If one is added
  later it belongs in a second job in this file, not a second matrix
  dimension — the Qt library step is Linux-specific.
- **No coverage, no linting, no docs build, no badge.** Each is a separate
  argument and this job exists to answer one question.

## 4. Tests

CI is not testable from inside the suite, and a test that parses the YAML to
assert what it says would pin the artefact rather than the behaviour — the
mistake `docs/decisions.md` records being retired on 2026-08-06 and
deliberately re-attempted only where there is an end condition
(`test_nothing_in_deckle_calls_this_yet`). There is no end condition here.

So there is no new test, and the acceptance in §5 is by observation of the
job. Two things make that honest rather than lazy:

1. **The suite that CI runs already contains the guards for the four bugs
   CI is being added to catch**: `tests/test_fixture_is_tracked.py`
   (R0.1), `tests/test_suite_imports_only_declared_dependencies.py` (R0.2),
   `tests/test_packaging_audit.py::test_the_spec_is_tracked_and_not_ignored`
   (R0.3), `tests/test_hardening_io.py::test_export_over_a_read_only_file_says_it_is_read_only`
   (R0.4), and `tests/test_repo_hygiene.py` (R0.5). CI's job is to run them
   somewhere else, not to duplicate them.
2. **The job is verified by making it fail on purpose** before it is
   trusted — see the `[HUMAN]` rows in §5.

## 6. Out of scope

- **The `requires-python` disagreement**, which this job makes visible and
  does not resolve. `pyproject.toml:7` says `">=3.11"`, `README.md:210` says
  "Python 3.11 or newer", and `run.bat:29` says "Install Python 3.12+". The
  matrix here is 3.12 and 3.14, so 3.11 remains claimed and untested. **This
  needs the owner**, and it is one of two answers: raise `requires-python` to
  `">=3.12"` and fix the README to match, or add `"3.11"` to the matrix and
  fix `run.bat`. Do not pick one inside this spec; record the question and
  move on.
- **A Windows job.** See §3.
- **Coverage reporting, ruff/mypy, the Sphinx `-W` docs build, a README
  badge, release automation, publishing to PyPI.** All separate; the docs
  build in particular is listed under F13.
- **Pinning dependency versions or adding a lockfile.** The suite has never
  been pinned and this is not the spec that changes that.
- **Caching anything but pip.** No apt cache, no PySide6 wheel cache.

## 7. decisions.md entry

Note: this spec stages only `.github/workflows/test.yml`, which does not
match the pre-commit hook's `\.(ts|js|py|rb|go|rs|cs|sql|sh)$` filter, so the
hook will **not** demand an entry. Write one anyway — a workflow is
infrastructure whose absence caused four of the five R0 items, and that is
exactly what the log is for.

```

- Symptom: No CI. ## 8. Traps

- **Do not add this before R0.1-R0.5 land.** It will be red on its first run
  with four unrelated failures, and the first thing anyone does with a CI job
  that is red on arrival is stop looking at it.
- **`python -m deckle` blocks forever.** It launches the GUI. On a runner
  that means a 20-minute timeout and a confusing log. Everything CI invokes
  is `python -m deckle.cli` or `python -m pytest`.
- **`QT_QPA_PLATFORM` must be an `env:` on the step, not a shell prefix
  inside a multi-line `run:`** — a prefix only applies to the first command
  on that line, and the suite would then pick up whatever the runner's
  default platform plugin is.
- **`cache: pip` without `cache-dependency-path` fails** on a repository with
  no `requirements*.txt`; setup-python raises "No file matched to
  [**/requirements.txt ...]". `pyproject.toml` is the file to hash here.
- **`apt-get update` before `apt-get install`**, always, or the package
  indices on the runner image can be stale enough to 404.
- **`pytest -k <pattern>` with no match exits 5, not 0**
  (`00-environment.md`). If a later spec adds a CI step that uses `-k`,
  that is the behaviour it relies on; this workflow deliberately runs the
  whole suite and has no `-k`.
- **`test_export.py`'s RSS test skips in CI** because `psutil` is not
  installed. That is by design; do not add `psutil` to make the skip go away.
- **`tests/test_golden_pinebox.py` skips** — it needs a 30 MB fixture that is
  deliberately absent. Expect it in the 22 skips.
- The runner is a non-root user, which matters:
  `tests/test_hardening_io.py`'s permission tests are meaningless as root
  (root ignores the mode and the export succeeds). Do not add a `container:`
  that runs as root.
