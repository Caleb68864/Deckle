# R0.4 — Restore a readable mode after the read-only export test

**Roadmap item:** `docs/ROADMAP.md` R0.4
**Depends on:** R0.1 (this test opens `tests/fixtures/sample.pdf`; without it
the module fails earlier, for a different reason)
**Blocks:** R0.6 — this is one of the two failures a CI job would report on
day one, and a CI job that is red on day one gets muted.
**Size:** S
**Decision needed first:** none.

## 1. Context

`tests/test_hardening_io.py::test_export_over_a_read_only_file_says_it_is_read_only`
checks a real, good behaviour: exporting over a file the user cannot write
is refused with a message that names the path and the reason, and the bytes
already at that path survive.

The behaviour is correct. The **test's own cleanup** is not. It sets the
file back to `stat.S_IWRITE`, which on POSIX is `0o200` — write for owner,
**read for nobody** — and then reads the file to make the last assertion.

So on Linux the test fails at its own final assertion, on a line that has
nothing to do with what it is testing. On Windows it passes, because
`os.chmod` there only manipulates the read-only attribute and `S_IWRITE`
means "clear it". The test was written on Windows and has been failing on
every Linux clone since.

Verified on the current tree:

```bash
QT_QPA_PLATFORM=offscreen .venv/bin/python -m pytest \
  "tests/test_hardening_io.py::test_export_over_a_read_only_file_says_it_is_read_only" \
  -q --no-header -p no:cacheprovider
```

```
E       PermissionError: [Errno 13] Permission denied: '/tmp/pytest-of-caleb/pytest-9/test_export_over_a_read_only_f0/locked_down.pdf'

/usr/lib/python3.14/pathlib/__init__.py:771: PermissionError
```

The failure is at `out.read_bytes()`, **after** the `finally`. Everything
above it passed: `rc == 1`, the message is actionable, and `"read-only"` is
in it. Confirmed independently by driving the same path outside pytest:

```bash
.venv/bin/python - <<'EOF'
import os, stat, tempfile, contextlib, io
os.environ["DECKLE_LOG_DIR"] = tempfile.mkdtemp()
from deckle.cli import main
d = tempfile.mkdtemp(); out = os.path.join(d, "locked_down.pdf")
open(out, "wb").write(b"%PDF-1.4 placeholder")
os.chmod(out, stat.S_IREAD)
err = io.StringIO()
try:
    with contextlib.redirect_stderr(err):
        rc = main(["export", "tests/fixtures/sample.pdf", "-o", out])
    after = stat.S_IMODE(os.stat(out).st_mode)
finally:
    os.chmod(out, 0o644)
print("rc=", rc, "mode after refusal=", oct(after),
      "read-only in err:", "read-only" in err.getvalue(),
      "bytes intact:", open(out, "rb").read() == b"%PDF-1.4 placeholder")
EOF
```

```
rc= 1 mode after refusal= 0o400 read-only in err: True bytes intact: True
```

Deckle is right; the cleanup is wrong. That distinction is the whole spec.

## 3. Change

Two edits to one file, plus one added test.

**Chosen: restore the literal `0o644`. Rejected: record
`stat.S_IMODE(os.stat(out).st_mode)` before the chmod and restore that.**
Recording is more general and it is worse here: it adds a stat the test does
not otherwise need in order to reconstruct a value that is already known —
`out.write_bytes` under this project's default umask produces exactly
`0o644` — and it puts the fix's correctness behind an extra step for a
reader trying to see why the old line was wrong.

### Steps

1. **`tests/test_hardening_io.py`**, in
   `test_export_over_a_read_only_file_says_it_is_read_only`, line 158.
   Replace:

   ```python
           os.chmod(str(out), stat.S_IWRITE)
   ```

   with:

   ```python
           # 0o644, not stat.S_IWRITE. S_IWRITE is 0o200 on POSIX -- write
           # for the owner and read for nobody -- so the last assertion
           # below could not open the file it was asserting about. On
           # Windows chmod only touches the read-only attribute and
           # S_IWRITE clears it, which is why this test was green on the
           # machine it was written on and red on every Linux clone.
           os.chmod(str(out), 0o644)
   ```

2. **`tests/test_hardening_io.py`**, immediately after that test, add:

   ```python
   def test_a_refused_export_does_not_change_the_files_permissions(tmp_path):
       """Refusing to write must not be a write of its own.

       ``export`` checks writability before it creates a scratch file, so
       nothing on the refusal path touches the mode -- and this pins that,
       because the obvious "fix" for a permission error is to relax the
       permission, and a tool that silently unlocks a file the owner
       locked has done something worse than fail.
       """
       out = tmp_path / "locked_down.pdf"
       out.write_bytes(b"%PDF-1.4 placeholder")
       os.chmod(str(out), stat.S_IREAD)
       try:
           rc = main(["export", FIXTURE, "-o", str(out)])
           after = stat.S_IMODE(os.stat(str(out)).st_mode)
       finally:
           os.chmod(str(out), 0o644)

       assert rc == 1
       assert after == stat.S_IREAD, oct(after)
   ```

   The mode is read **inside** the `try`, before the restore. Reading it
   after the `finally` would measure the cleanup.

### The added one

`test_a_refused_export_does_not_change_the_files_permissions`.

**It passes on the unfixed tree.** Say so rather than pretending otherwise:
the property it asserts is already true (measured — `mode after refusal =
0o400`). It is added because step 1 puts a hard-coded `0o644` into the
neighbouring test's cleanup, and the next person maintaining this file has a
reason to believe modes are something the tests are free to move around. The
test says which mode changes are the test's business and which would be a
defect in `export`.

Mechanically confirm it is not vacuous by mutation: change
`deckle/core/export.py`'s `_check_writable` call site so the export chmods
the target before writing, run the test, see it fail with `0o644` in the

## 8. Traps

- **`stat.S_IWRITE` is not "writable".** It is `0o200` alone. `S_IREAD |
  S_IWRITE` would be `0o600` and would also work; `0o644` is chosen because
  it is what `Path.write_bytes` produced in the first place under the
  project's default umask.
- **Do not read the mode after the `finally`** in the new test. It is the
  restore you would be measuring, and the test would pass no matter what
  `export` did.
- **Running the module as root makes both tests meaningless** — root ignores
  the permission bits, `export` succeeds, and `rc == 1` fails. This is not a
  regression; do not "fix" it by loosening the assertion. CI in §R0.6 runs as
  a non-root user.
- On Windows `chmod` cannot make a file unreadable at all, so the final
  `read_bytes` assertion has always been reachable there. Do not conclude
  from a green Windows run that the fix was unnecessary.
- The autouse `_isolated_log` fixture redirects `DECKLE_LOG_DIR`; the new
  test must be in this module (not a new file) to inherit it, or it will
  write to the developer's real diagnostics log.
- `python -m deckle` launches the GUI. Everything here goes through
  `deckle.cli.main(...)` in-process, which is what the module already does.
