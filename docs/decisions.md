## 2026-09-10 — H2: a refused import was the one failure nobody was told about
- Symptom: `ImportView` declares two outcomes and emits both — `imported` carries the pages, `failed` carries an error message. `MainWindow.__init__` connected the first and not the second. So a failing import updated the import row's own small label and nothing else, while the status bar went on saying *"Import a PDF or a folder of images to begin."* — an instruction the user had just tried to carry out and been refused for. Every other failure in the app reaches the status bar: a schedule that could not be saved, a project whose source is missing or has changed, a drop of something Deckle does not take. Import was the gap, and it is the first thing anyone does.
- Fix: `failed` connects to `_on_import_failed`, which stores the message and logs an `import_failed` event, and `_refresh_status_message` grows a fourth rung.
- Decided, and not the one-line version: the message is **state the refresh reads**, not a `showMessage` written past it. `status_bar.showMessage(...)` at the connection would have been shorter and is what the drop-rejected and project-open paths do — but printer enumeration runs on a background thread and ends in `_apply_printers`, which calls `_refresh_status_message()`. An import that failed while that query was in flight would have had its message replaced a moment later by an unrelated one, with nothing left to say it ever appeared. The module already keeps the status bar to one writer for exactly this reason; `_printer_message` is the precedent and `_import_message` is its twin.
- Decided: the refused import **outranks the printer fault** while it lasts, and is cleared by the next successful import. A printer fault is a standing condition the user cannot otherwise see; a refused import is the answer to something they did a second ago, and with no document loaded it is the only one of the two they can act on. When it clears, the printer fault comes back.
- Surfaces: adding one attribute to `MainWindow` reddened **eleven** tests in `test_hardening_printing.py`, because `_FakeWindow` is a hand-built stand-in for a window with no declared surface — the shape the second scan's Q1 measured. The fix is one line in the double; the finding is that nothing but a run of the suite says the double has drifted.
- Watch: **an in-process `MainWindow` is not safe in this suite, and the second scan's clearance of it is only true standalone.** The first version of this file constructed one in-process — passing alone in 7.7s, on the strength of that clearance — and hung the full run at around 37%. A `MainWindow` built after other tests have written into the shared scratch data root finds a never-saved autosave and offers it back through a modal that nothing in a pytest process is going to answer, which is maintainability row 1 arriving by a route the clearance did not cover. Rewritten as an out-of-process probe with its own data root, like the four that were already there; the file records why. Five of its six tests fail before this change (the sixth guards the clearing behaviour, which has nothing to clear before it).

## 2026-09-10 — S9: `python -m deckle --help` never returned
- Symptom: found from live evidence rather than from reading. `ps` on the development machine showed `.venv/bin/python -m deckle --help` with an elapsed time of **23 hours 54 minutes**, left by an earlier session. `app.main.main` handed `argv` straight to `QApplication`, which silently ignores what it does not recognise, and then called `exec()`. There was no argument parsing on that entry point at all — no `--help`, no `--version`. The single most reflexive thing anyone does with an unfamiliar command produced a terminal that never came back and printed nothing; with `QT_QPA_PLATFORM=offscreen` inherited from a previous command it opened an invisible window and blocked, which is exactly the 23-hour process.
- The asymmetry is the tell: `python -m deckle.cli --help` has always worked, because `cli/options.py` builds a real parser. Only the GUI entry point — the one the README names first — had nothing. It compounds C4: the `deckle` console script is named in a dozen documents, so a reader reaches for `python -m deckle` as the documented equivalent and lands here.
- Fix: `deckle/__main__.py` answers `-h`, `--help` and `--version` **before** `QApplication` exists, and `python -m deckle` now goes through `run()` rather than straight to `app.main.main`.
- Decided, and worth saying why it is not an `argparse` parser: **Qt owns this command line.** `-platform`, `-style`, `-stylesheet` and the rest are consumed by `QApplication` and work today; a strict parser would reject them for the sake of arguments nobody passes. So the interception is a small closed set of three flags, and everything else is still handed to Qt untouched. The three intercepted are the three that have an answer this side of the event loop.
- Surfaces: `--version` prints exactly what the CLI's does, via `core.about.version_string()`, and a test asserts the two are equal rather than merely both non-empty. The GUIDE tells anyone reporting a problem to send `deckle --version`; two entry points that disagree turn one support request into two. `about` reads versions from installed-distribution metadata rather than by importing the packages, so this path does not import PySide6 either — pinned by a probe that runs the module and then asks the child whether `PySide6.QtWidgets` is in `sys.modules`.
- Watch: **the failure is not an exception, it is a process that does not end**, so the tests shell out and a timeout *is* the regression. Before the fix all six failed by hanging for the full 45s each, 271s for the file; after it the file runs in 1.3s. `QT_QPA_PLATFORM=offscreen` is set in the child on purpose: without it a headless box fails on the platform plugin instead, which is a different failure that would mask this one.

## 2026-09-10 — P3: nothing told the printer what paper the plan was for
- Symptom: `setPageSize`, `setPageLayout` and `QPageSize` appeared **nowhere** in `deckle/`, and Deckle draws its own print dialog rather than opening a `QPrintDialog`, so no code and no user ever told the driver what page a job was for. Every print went to whatever the driver defaulted to — portrait A4 or portrait Letter.
- Why it only became a defect this week: **B6.** Before it, `_paint_rendered_page` fitted the rasterised sheet into `printer.width()`, so a page-size mismatch came out silently *scaled* — wrong, but whole. B6 (settled 2026-09-08, entry below) made the painter draw one inch of design as one inch of paper from `(0, 0)` and stop reading `printer.width()` at all, which is right and is what the whole program already assumed. In exchange, a mismatch stopped being scaled and started being **clipped**. Measured: a folio (letter-landscape) plan on a default portrait page loses 180pt — 2.5in — off its width; a Letter plan on an A4 default loses 17pt. Folio is not hypothetical: `SaddleStitchStrategy.impose` warns when the paper is *portrait*, because folio is meant to run on landscape stock, and a default `QPrinter` is portrait.
- Checked against the B6 record rather than against intuition, because B6 is what made this bite. B6's stated trade was "content inside the printer's non-printable border is clipped rather than shrunk to fit, which `clipped_by_imageable_area` already warns about and the preview already draws" — a millimetre at the edge, visible before the paper is spent. That reasoning holds for the *border*. It does not extend to the page size, and neither of the two clip warnings can see this one: `preview_view.clipped_by_imageable_area` and `clipped_by_page` are both computed in `plan.paper_pt` coordinates and *assume the device page is the plan's paper*. So the residue B6 accepted was a warned millimetre; what was actually there was an unwarned 2.5 inches. Setting the page size does not reopen B6 — it makes B6's assumption true, which is the condition under which painting 1:1 at the corner means what it says.
- Fix: `_apply_paper(printer, plan.paper_pt, printer_name)` on both submission paths — `_submit_chunk` (every manual pass, and the proof) and `submit_duplex` — immediately after `setFullPage(True)`, which must stay set first so the margins can be zero and `(0, 0)` stays the physical corner.
- Surfaces: the layout is built **portrait-side-up plus an orientation**, not as a custom size with the numbers swapped. Qt stores standard sizes portrait and carries the turn in `QPageLayout.Orientation`, so `QPageSize(QSizeF(612, 792))` + `Landscape` is *"Letter, turned"* while `QPageSize(QSizeF(792, 612))` is 792x612 points of nothing in particular; a driver does something far more predictable with the first. `FuzzyOrientationMatch` is what performs that naming, and it is load-bearing for a second reason: Deckle's A4 is 595.276x841.89pt and Qt's is 595x842, and 0.28pt must not turn A4 into a custom size.
- Surfaces: a printer with a fixed paper list can refuse, and Qt reports that **only** through `setPageLayout`'s return value — precisely the kind of answer that gets dropped. The job still goes: declining to print is worse than printing on the paper the operator has loaded. But the refusal is logged as `print_paper_size_refused`, because it is the one warning that the sheet about to come out will not measure what the schedule says it does.
- Watch: **three test stubs had to grow a method, and one of them proves why the probe must not trust an exit code.** `tests/test_proof_sheet.py`'s `_StubPrinter` had no `setPageLayout`; the resulting `AttributeError` was swallowed whole by `submit_proof`'s broad `except Exception`, which turns it into `PrintResult.error` — a failing stub that reports itself as an ordinary print failure rather than as a broken test. The new tests in `tests/test_print_paper_size.py` therefore assert that the rig **reached** the subject (the renderer was called for the expected sheet and side) before asserting anything about what the printer was told, and they read the paper back off the real `QPageLayout` the production code built instead of recomputing it.

## 2026-09-10 — P2: the flip axis is a measured fact, not a geometric one
- Decision, and whose: **the owner's.** `rotate_backs = profile.flip_axis != duplex_flip_edge(plan.paper_pt)`. Two sites had been computing what looked like the same quantity and were not: `printing.py` used `profile.flip_axis == "long"` and `schedule.py` used `duplex_flip_edge(plan.paper_pt)`. Neither is sufficient alone, and the owner's answer is to compare them.
- Symptom: every back side printed upside down, for the whole run, on the most common job Deckle does. `flip_axis` is a **measured** fact about the machine — which named edge the operator physically turns the stack about. `duplex_flip_edge(paper_pt)` is a **geometric** fact about the job — which named edge is the sheet's vertical one, and so the one it must turn about for the backs to land upright. They share a vocabulary (`"long"`/`"short"`) and are different quantities. A long-edge flip lands the backs upright on portrait paper and inverted on landscape; the old rule said "rotate" in both cases, so it was right for landscape (folio) and exactly inverted for portrait (gutter shift) — including under `generic_face_down_reversed`, the preset `resolve_profile` falls back to when a calibration file cannot be read.
- Already settled, and followed rather than re-decided: the 2026-08-06 entry below ("The exported PDF never said how it was meant to be printed") had established the geometry in full — "the spine is vertical on the sheet under every scheme Deckle imposes ... so the sheet must turn about its VERTICAL edge ... so either constant is wrong for half of Deckle's own output" — and made `duplex_flip_edge()` the single source both the exporter's `/Duplex` entry and the schedule read. That record did not reach `rotate_backs`, which is the one consumer that also has to know what the *printer* does. The owner's formula is that record's rule applied to the remaining consumer: rotate exactly when the machine's axis is not the sheet's vertical one.
- Fix: one line in `plan_passes`, reading `plan.paper_pt` alongside the profile. Everything downstream — `pass_export`, `export(rotate_180=)`, the Qt backend, `PrintSession` — already consumed `PrintPass.rotate_backs` and recomputed nothing, so there was exactly one place to change. Checked rather than assumed: `cli/report.py`, `cli/commands.py`, `core/report.py` and `core/session_log.py` all *report* `flip_axis` verbatim, which is right; none derives geometry from it. `printing.py`'s ordering table and the prose at its line 28 stated the opposite rule in words and were rewritten, along with the same claim where it had been copied into `profiles.py`, `schema.py`, `print_session.py`, `export.py`, `app/backend.py`, three test files and the CHANGELOG. A docstring left saying the old thing is the next contradiction, and this one had been repeated in ten places.
- Surfaces: **the reload instruction was already right and stays untouched.** `_back_instruction` tells the operator to flip on `profile.flip_axis`'s edge — their machine's calibrated behaviour — and the software compensates in `rotate_backs`. Telling them to flip about the vertical edge instead would double-correct. **The SS-04 zero-diff seam is intact**: it constrains what `plan_passes` reads off a `Sheet`, and `paper_pt` is a property of the `SheetPlan`. Both halves of `test_spec_residue.py` were re-run rather than reasoned about.
- Watch: **the bug was invisible for months because every test used one orientation.** `test_flip_axis_long_yields_rotate_backs_true` and its short-edge twin both ran on portrait Letter and both asserted the inverted answer; six further tests across four files had been written against them. The replacement is a four-row parametrised table naming the geometry in each case, plus two tests that pin the *shape* of the rule — the same printer must give different answers on the two papers, and the same paper different answers for the two printers, so neither quantity can be dropped again without a failure. The whole table is repeated end-to-end in `test_cli_passes.py` against real `/Rotate` values through `deckle export --pass back --landscape`. Mutation-checked: restoring `flip_axis == "long"` fails 12 tests across five files.

## 2026-09-09 — B37: the app asks how many sheets came out, because it cannot see the tray
- Decision, and whose: **the owner's.** "I'd like a popup that lets me choose how to proceed, so I can tell the app if I got the pages or need to reprint." The roadmap row had proposed advancing the cursor by `result.submitted`. That is a guess, and it was declined.
- Symptom: `PrintResult.submitted` is set carefully on both branches of `QtPrintBackend.submit` to say how many sheets physically printed, and **no caller read it**. `PrintSession._submit_chunk` returned on `result.error` before `sheet_cursor += len(chunk)`, so a chunk that printed and then failed to be written to the session log — which is a hard constraint, not a best-effort trace, and stops the run on purpose — left the cursor sitting behind paper that was already in the tray. A resume fed those sheets through a second time, onto a stack the operator had by then reloaded. Fixing B4 closed the traceback route into this; the route through the error branch was untouched, and had been pinned by a strict `xfail` rather than guessed at.
- Fix: `PrintSession` gained `ask_sheets_printed`, an injected callable handed a frozen `UnrecordedSheets` (printer, pass index, side, the chunk's sheet indices, `submitted`, and the backend's error text) and returning a count, `0`, or `None`. The answer is what moves `sheet_cursor`. `PrintDialog` supplies the default implementation and hands it to every session it builds — fresh **and** resumed, since `load` rebuilds a session field by field and is exactly where a seam goes missing on one path only.
- Why asking is the right shape for *this* program, and not merely the owner's preference: the count of sheets in an output tray is not derivable, and Deckle already knows that. `resume(sheets_completed)` has taken it as caller-supplied ground truth since SS-11, with the reason in its docstring. B37 is that same fact arriving at a different moment. Answering it at the moment of failure is strictly better than at the next resume: the operator is standing at the printer, the paper is in front of them, and the number lands in the state file rather than being reconstructed from memory tomorrow. Reusing `ask_resume_count`'s three-way shape — count / `0` / `None` — is deliberate. Zero is a real answer (nothing came out, reprint the lot) and cancel is not; that distinction was fixed earlier the same day, and inventing a second dialect for the same question would have taught the operator that the two answers mean different things.
- Surfaces: **The offline branch is never asked.** Painting that raised leaves `submitted` at 0 — the chunk may have died on its first page or its last, nothing is known to have come out, and there is nothing to count. Interrupting someone to answer a question the program cannot use is how a prompt gets clicked through. **Declining, and having nobody to ask, both leave the cursor put.** The session does not fill a silence with `result.submitted`; that is the guess this row was opened rather than made, and reprinting a chunk costs paper where advancing past sheets that never came out costs the book. **The pass does not advance even when the count fills it.** The run is stalled; walking on to the backs while the fronts are still an open question is the ruined-stack failure the whole `plan_hash` check exists to prevent. **The answer is clamped, not refused.** More sheets cannot come out than went in, and `start()` promises not to raise — `resume` raises on a negative because its caller can still show a message, and this one cannot.
- Surfaces: **The core stays Qt-free.** `UnrecordedSheets` and the seam live in `deckle/core/print_session.py`; the modal and its prose live in `deckle/app/views/print_dialog.py`, the way every other confirmation in that dialog already does. The prose itself is `unrecorded_sheets_prompt`, a pure function beside `select_preselected_printer`, so the wording is testable without a display — the situation before the question, the printer and pass named, the backend's own error quoted, and what Cancel does spelled out. **The CLI needs none of it**, and this was checked rather than assumed: `deckle print` plans passes and optionally writes one PDF per pass, submits nothing, constructs no `PrintSession` and never holds a `PrintResult`. Submission is the one part of the print path that is not Qt-free, which is the reason the CLI does not do it.
- Watch: **A number nobody reads looks correct.** `submitted` was set on both branches, documented on both branches, and asserted by three tests — and the whole time it went nowhere. The tests checked what the backend *reported*, and the defect was one call up the stack, in what the caller did with it. The strict `xfail` was the only thing that said so; it is now a passing test with eleven siblings, and the four load-bearing edits were each mutation-checked by reverting them (the cursor advance fails 7, the fresh-session wiring 1, the resumed-session wiring 1).

## 2026-09-09 — N14: `profile set` shows the diff and refuses, rather than refusing
- Symptom: `PrinterProfile.save`'s docstring calls a calibration the most expensive data Deckle holds — it is measured with a ruler and cannot be recomputed from anything — and the CLI had no way to see a profile, let alone write one. Adding a `set` that overwrote silently would have made the CLI the fastest way to destroy the one thing in the program that costs paper to reproduce.
- Decision: editing a saved profile prints the exact before-and-after of every field that would change and **exits 1**; `--force` applies it. ## 2026-09-09 — The desktop shell: menus, drops, unsaved work, one pass, a proof (N7/N8/N9/N13/N4/N3)

*Six roadmap §3b rows, all verified still open against the tree before starting: no `QMenuBar` anywhere, no `acceptDrops`, no `setWindowModified`, no About or diagnostics affordance, no single-pass export in the app, no proof from the print dialog.*

- **The menu is data, not construction.** `deckle/app/menus.py` holds `MENUS` — label, method name, key sequences — and `build_menu_bar` is the only part that touches Qt. Two failures that are silent at runtime become failures at import: an entry naming a method `MainWindow` does not have, and two entries claiming the same key. Qt does not refuse an ambiguous shortcut; it picks one of the two actions, or neither, and says which never.
- **The grid keys belong to the grid.** `R`, `S` and `Del` are one `QAction` each, shown in the Edit menu and added to the page list with `WidgetWithChildrenShortcut`. A bare letter bound window-wide competes with every spinbox in the settings column, and the menu is still where somebody finds out the key exists.
- **`Del` is spelled as skip.** Deckle has no destructive page removal — a skipped page keeps its slot, which is the whole reason un-skipping restores its position — so binding Delete to a new destructive verb would have been inventing a feature under cover of a keyboard shortcut. It is the same command as `S`.
- **Recent projects gave up its button.** It was a button on the argument that a submenu would bury the list one click deeper than the dialog it exists to replace. True when there was no menu bar; false now that File is one keystroke away and holds every other way into a document.
- **A drop takes one item, and asks.** `classify_drop` accepts exactly one path: two PDFs look like one gesture and are two imports, which `ImportView` runs one thread at a time, and a queue that silently picks an order is worse than a refusal that names the rule. A drop onto an *empty* Deckle imports without asking — there is no question to put. A drop onto a document that has pages asks add-or-replace, which is the same choice the import bar's checkbox offers; picking one silently either throws the document away or buries a replacement at the end of it.
- **Dirty is identity, not equality, and autosave is not a save.** `AppState.dirty` is `self._project is not self._saved_project`. `Project` is frozen, so undo restores the very object that was saved and undoing back to it clears the marker for free. A recovered autosave opens *dirty* (`mark_unsaved`), because that work exists nowhere but in memory.
- **The close prompt can actually refuse the close.** `closeEvent` was documented as always accepting, on the grounds that refusing over a running render would trap the user. Unsaved work is the one reason worth refusing for; a prompt that could not stop the close would be a notification. Cancel is the default button, so a reflexive Return keeps the work. A clean or empty document closes without a word.

The CLI previously assembled its own `export` call, which is exactly the shape of duplication that lets two front ends disagree about one printer while both look right. The suggested name carries the side (`-front.pdf`), because the two files are indistinguishable once they leave the machine and printing the back pass first ruins the stack.
- **A proof is not a job.** The print dialog's proof checkbox goes to `QtPrintBackend.submit_proof`, not through a `PrintSession`: one face, no reload, no back pass, and — the point — no resumable session left on disk for the next print dialog to offer to "finish". It carries no back-offset correction either; the offset moves the image and would read as the printer having scaled it. The sentence telling the user what to measure is `export.proof_rule_advice`, shared verbatim with the CLI's `--rule`, so a user who has done the check once recognises it.
- **About is offline, and says so.** `deckle/core/about.py` holds the version lines `--version` prints, so a report built in the app is comparable with one built at the shell. There is no update check, no URL, and a test asserts both: no `https?://` in the text, and importing the module loads no `urllib`/`http`/`socket`/`ssl`. **Help → Open diagnostics folder** creates the directory if nothing has been logged yet and reports the path in the status bar when the desktop refuses to open it — the path was the answer the user needed; the folder opening was a convenience.
- **Watch:** three GUI probes had to gain `confirm_discard_changes = ... "discard"` because a modal appeared where none had been before, and one of them hung for the full 180s subprocess timeout rather than failing. **A suite that got eight times slower was the only symptom**, the same signal as the 2026-08-04 printer-enumeration entry. Adding a modal to a shutdown path is a hang, not a failure; inject the answer at the same moment you add the question.

## 2026-08-07 — Every store Deckle keeps destroyed the old copy before writing the new one
- Symptom: All three JSON stores -- project files, printer profiles, the recent list -- were written by opening the target and truncating it. Everything after that point (a full disk, a dropped share, a killed process) leaves the file as a prefix of the new document, which is not valid JSON and will not open. **Autosave is where this turns from untidy to self-defeating**: it runs unattended on a daemon timer thread, and its stated promise is that a killed process loses at most the last half-second of edits -- but a process killed *during* the write lost the whole project, because the recovery file was the thing being truncated. The one failure autosave exists to survive was the one it could not.
- Fix: `paths.write_text_atomic` -- temp file beside the target, `fsync`, `os.replace` -- and all three stores go through it. One implementation rather than three, for the same reason `config_dir` is one: three copies of a durability decision is three chances to get one of them wrong. The temp file goes in the target's own directory because a cross-filesystem rename is not atomic, and the `fsync` is for ordering rather than durability -- without it the rename can reach the platter ahead of the content it renames, and the target ends up pointing at a file of zeros.
- Surfaces: Profiles are the worst case and it is not close. A calibration is the only data Deckle holds that is not derived from anything -- it comes from printing a target, measuring by hand, and reprinting when the numbers are wrong -- and `PrinterProfile.load` has no tolerance for a corrupt file the way `recent.load` does. So a torn write did not degrade that printer to "uncalibrated"; it raised, and the printer stayed unusable until the user found and deleted a file in a directory they have never opened. For `recent` the failure is the opposite shape and just as bad: `load` reads a malformed store as empty *by design*, so a torn write silently erased the history that `existing` and `forget` are carefully arranged never to erase. Two files also carried the pass-1 defect: `_layout_to_dict` and `PrinterProfile.save` each converted one named tuple field on the way out, which `json` was doing for every field anyway -- and naming one field on the way out is what made it look correct to name one field on the way in. Both now convert nothing, and `PrinterProfile.load` converts every list, closing the half of its own 2026-08-06 lesson that was applied to unknown keys but not to tuples.
- Watch: **The first seven tests written for this all passed against the unfixed code.** They injected the failure at `json.dumps`, which runs *before* the file is opened, so nothing was ever truncated and nothing was ever at risk. Sixth vacuous test, same root cause as the other five: asserting at a layer above the one where the bug lives. The second attempt injected at the target *path*, which went red correctly and then went red again after the fix -- because an atomic writer never opens the target, so the fault never fired and the save simply succeeded. What finally works is arming the fault around the save call and failing whatever file gets written next, which is the only formulation that does not name a mechanism: a truncating writer dies holding the store open, an atomic one dies holding a temp file, both raise, and only one loses data. Worth keeping in mind generally -- **a fault-injection test that names the file is a test of the implementation, not of the property.**

## 2026-08-07 — Two render threads and a native fault, which is what "it randomly closes" looks like
- Symptom: pdfium's rendering is not thread-safe and it does not fail politely. Two concurrent rasterizations produce either `PdfiumError: Failed to load document (Data format error)` or `OSError: exception: access violation reading 0x0` -- a **native fault, not a Python exception**: no traceback, nothing in the log, and the process gone. - Surfaces: **Deckle reaches this through ordinary use, not an unusual one.** Both views that render do it on a background `QThread`, and both supersede a running job identically -- set the outgoing worker's `cancel` flag, then start the next thread *without waiting for the old one to stop* (`preview_view._start_render`, `arrange_view._request_thumbnails`). The cost of serialising is that renders no longer overlap -- they contended for the same cores anyway, and a superseded render drops out at its next checkpoint. The matrix negates its angle once, in the one place that builds it. `_pdfium_rotation` passes degrees.
- Surfaces: **No dimension arithmetic changed, and that is the part an implementer will assume is broken and rewrite.** `_source_dims` swaps for a 90/270 user rotation and the policy branch swaps again when it fires; composing two swaps is already identical to "swap iff the total is 90 or 270". A non-quarter-turn stored value snaps to the nearest quarter rather than raising -- 45 has no correct answer, and a `KeyError` out of a thumbnail worker is not the way to say so. Composition, not replacement: a portrait page the user turns 90 IS landscape, so under `rotate` the policy turns it again -- net a half turn -- and a page turned 270 comes back upright, which a `rotate_deg = 90` assignment could never produce.

The end-to-end guard is that the thumbnail and the exported sheet put the ink in the same corner for all four turns: the grid is where the user turns the page, the sheet is what reaches paper, and they were rendered by different code turning opposite ways -- while for rotated pages the grid did not render at all, so nobody could see the disagreement.

## 2026-09-09 — A folder of scans was stored in a cache, so Deckle deleted its own sources
- Symptom: Two ways a `.deckle` named a file that was not there, both created by the loader at the moment a `SourceRef` was built. `load_pdf` stored the path exactly as typed, so `deckle impose ./book.pdf -o book.deckle` recorded `"./book.pdf"` and the project opened only from the directory it was made in -- reported as "a source file is missing", naming a file that had not moved. And `load_image_dir` merged a folder of scans into one normalised PDF under `<tempdir>/deckle_import_cache/` and pointed every `SourceRef` at *that*, under a 2 GB least-recently-used budget: the eviction pass, run by the next unrelated import, preferred the least-recently-used entry, which is exactly the project you have not opened in months. The OS emptied the directory on the next reboot regardless. The user's own folder of images was never recorded anywhere, so the dangling reference could not even be relocated.
- Fix: `_read_pdf_pages` absolutises once, above the loop. Image imports write into `paths.data_dir("imported")`, named by the merged PDF's own sha256, and nothing prunes it.
- Surfaces: **`abspath`, not `realpath`.** Joining against the cwd is the fix; resolving symlinks as well would file scans under a symlinked `~/Books` as `/mnt/volume-3/...`, which is the same file only until the mount point changes, and is not the name the user chose. `project_io._path_within_roots` still uses `realpath` on both sides, where "is this the same file" is the actual question. The call is in `_read_pdf_pages` and nowhere else: `os.path.abspath("")` is the current working directory and `BLANK_SOURCE_PATH` is `""`, so the same line applied to an inserted blank would turn every blank into a reference to whatever folder Deckle was launched from, and `is_blank_page` tests for equality with `""` -- `load_project` would then start demanding those folders exist as files. **No migration.** A `.deckle` already holding `./book.pdf` keeps holding it and keeps working where it worked before; rewriting stored paths on load would be `load_project` silently editing the document, and on save would change a file the user did not ask to change. The next impose or Save writes an absolute path, and that is the whole migration.
- Watch: **The store trades a bound for durability, and that was a judgement call, not a bug fix.** The 2 GB budget was red-team advisory A-7 -- "heavy image import otherwise accumulates silently in temp" -- and it is now gone; the store grows with the number of *distinct* image folders imported. That is deliberate: a stale gigabyte in `~/.local/share/deckle/imported` is recoverable by hand, and a saved project whose only source has been deleted is not. Content-addressing answers the repeat that would actually pile up -- the same book imported again after a cancelled job, or to start a second project from it, normalises to identical bytes and reuses the one file already there -- and dedupe is "leave the existing file alone", never "overwrite it with the same thing", because another project is already referencing it. The roadmap's own open question asked something narrower (B26, ROADMAP §6: spool the normalised PDF *beside the project*?) and its spec recommended that branch; it was **not** taken here, because at import time there is no project path, its desktop half means `save_project` rewriting `SourceRef.path` for every page during a save, and it puts a file the user did not create into the user's own folder -- a product decision that is still open and now a portability feature rather than a data-loss bug. `evict_lru_files` is untouched and still bounds the *export* cache, which references nothing.
